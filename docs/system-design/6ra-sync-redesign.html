AWS::Lambda
Webhook Receiver 💀
Validates notification (incl. resourceData schema), enqueues, returns 200.
▶
Failure modes (evidence from 6ra.4 / 6ra.6)
  • resourceData required by schema → every real OneDrive webhook 400. OneDrive notifications carry no item info — the schema was impossible-by-design.
  • Fire-and-forget enqueue + immediate 200 — Lambda event-loop freeze can lose the SQS send.

→ Superseded by 6.6.4 webhook receiver (bell only, enqueue-then-ack within 3s).

Processor 💀
Consumes ingest queue; downloads PDF, uploads to S3, writes file_record.
▶
  • Carried its own token-refresh copy (with sync-worker + api middleware = 3 copies).
  • Revalidates + re-fetches everything — the “current processor’s sin”.

→ Superseded by adapter-owned fetch+gate+land (5.1.1) + staging dispatch seam (5.2.3).

ingest-onedrive resourceData zod schema 💀 dies no equivalent — bell-only payload accepted 400 “Invalid notification payload” root cause; OneDrive webhooks carry no item info (impossible-by-design).
Fire-and-forget notification enqueue 💀 dies 6.6.4 webhook receiver — enqueue-then-ack (2xx within 3s) Lambda event-loop freeze silently loses SQS sends.
3× duplicate token-refresh copies (api/onedrive-middleware, sync-worker, processor) 💀 dies 6.6.1 — single home, per-profile CAS store One token lifecycle, not three. Stale copies die with their owners (open 6.6.1 Q4).
sync-worker pending-status double-write 💀 dies adapter lands + emits → staging indexes (single path) “Write record, then processor overwrites” hazard.
Webhook-as-data path (metadata from webhook) 💀 dies webhook = bell only; delta = the data path (6.6.3) Discovery §1: notifications include no change information.
Processor Lambda (ingest queue consumer) ♻ superseded adapter fetch+gate+land (5.1.1) + staging dispatch seam (5.2.3) Split by ownership: content fetch is adapter-owned; the Lambda shell becomes the thin dispatch seam.
Job machine: sync_jobs outbox → DDB stream → sync-relay → sync-jobs queue → sync-worker + /sync/jobs/:jobId polling ♻ superseded “Sync Now” = catch-up delta-trigger event (6.6.5); plugin polls the files feed Locked decision §9: no job machine. Sync-relay and sync-worker die together with the outbox.
Producer-push into consumer queues (worker → ingest queue; relay → sync-jobs queue) 💀 dies domain events to registry; consumers forward onto their own queues “A queue is a delayed void call into a domain — never a conversation mediator.”
Old S3 keys (handwritten/… prefix, no layout version) + pending records 🕓 interim staging/v1/<profileId>/…; reindex by 5.2.2 Layout version in the key; additive v2. Cleanup-now vs reindex open (5.2.1 Q5).
Standalone “API service” ♻ superseded two surfaces: adapter /onedrive/* (6.6.5) + staging /files (5.2.4) Endpoints owned by the service that owns the data. Single base URL kept — deployment shape (gateway prefix routing) still open.
Third profile service concept 💀 not built neutral profile record in core + adapter-hosted surface (common envelope) Decided: no third service; folder-structure pushed-event is a future profile-service extension point.
GitHub App + JWT identity ✅ kept as-is, shared middleware on the surfaces Deferred — orthogonal to the sync redesign.
S3 lifecycle expire-staged-pdfs (90 days) ✅ kept unchanged; TTL on file_records aligned with it Purely time-based retention, no per-file ack.
SQS DLQs + CloudWatch alarms + SNS email ✅ kept staging DLQ (5.2.3 redrive) + alarms Same reliability fabric; queues re-homed to owning domains.

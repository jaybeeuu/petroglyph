external
OneDrive + Microsoft Graph
Drive-root subscription · delta verb · delegated OAuth.
▶
Ground truth (6ra.6, research complete)
  • Webhooks carry no change info — no item id, no changeType, no resourceData. Verbatim: “the notification doesn’t include any information about the changes… use the delta verb”. The bell-only contract.
  • Delta is the data path: first call = full enumeration; page @odata.nextLink → @odata.deltaLink; opaque tokens; deleted:{} facet; 410 Gone / syncStateNotFound ⇒ full resync.
  • Subscriptions expire (~3 days driveItem); renew via PATCH before expiry; 404 on renew ⇒ recreate (the only removal detector).
  • Latency avg <1 min, max 6 hours ⇒ periodic catch-up sync is the reliability net, not optional.
  • Personal OneDrive: root or subfolder subscriptions · OneDrive for Business: root only. No file-level subscriptions.
  • Auth: delegated files.readwrite offline_access, refresh-token rotation.

6ra.5.1 umbrella 6ra.6.1–6.6.5 6ra.5.1.1 glue

The single home for all OneDrive/Graph knowledge: OAuth, subscriptions, webhook, delta walk, and the fetch + gate + land routine. It talks to the outside world and emits facts (business events) to the central registry — it never pushes into another domain’s queue. This domain owns the /onedrive/* surface the plugin talks to for anything source-specific.

6ra.6.2
Subscription management
Create / renew / recreate; stored-subscription registry.
▶
Responsibility
  • Create subscription; renew via PATCH before ~3-day expiry (guided by subscriptionExpirationDateTime in every notification).
  • Recreate on PATCH 404 — for driveItem this is the only removal detector (subscriptionRemoved/missed are Outlook-only).
  • reauthorizationRequired lifecycle notification → refresh tokens.
  • Registry (per profile: subscriptionId, clientState, resource, expirationDateTime) that the webhook receiver validates inbound bombs against.
  • Business = root-only subscriptions; Personal = root or subfolder.
Status

Planned — description + tests defined, no plan doc yet. Blocked by 6.6.1.

6ra.6.4
Webhook receiver 🔔
Receives Graph notification POSTs — bell only, no content parsing.
▶
Responsibility
  • Validation-token dance at create-time: POST ?validationToken= → 200 text/plain, URL-decoded echo, within 10s.
  • Validate inbound subscriptionId + clientState against the registry (6.6.2); reject unknown subscriptions.
  • Ack contract: enqueue delta-trigger synchronously → 2xx within 3s; 5xx if unqueued.
  • Emits “delta trigger” events consumed by delta sync (6.6.3).
Kills
  • ingest-onedrive resourceData zod schema — the 400 “Invalid notification payload” root cause.
  • Fire-and-forget enqueue — the lost-SQS-send Lambda bug.
6ra.6.3
Delta sync + change-token mgmt
The data path. Walks Graph delta; emits FileChangeEvent.
▶
Responsibility
  • First run (no token) = full enumeration; page @odata.nextLink ($skiptoken) until @odata.deltaLink ($deltatoken).
  • Store opaque token per profile — copy URL verbatim, never re-append query params.
  • deleted:{} facet → deleted change; 410 Gone + empty-token Location / syncStateNotFound → full resync with token cleared.
  • Normalises relativePath — OneDrive parentReference.path never leaks.
  • Walker stays pure/fast — no content fetching, no S3, no token logic beyond the delta call.
Emits

FileChangeEvent { profileId, changeType, itemId, name, relativePath, mimeType? } — adapter-internal, not registered.

6ra.6.5
Adapter user surface /onedrive/*
Auth bootstrap, sync control, profiles, status — common envelope.
▶
Responsibility
  • /onedrive/auth-url + /onedrive/connect: OAuth bootstrap → exchange code → persist initial tokens (refresh/use is 6.6.1’s job).
  • Sync control: “Sync Now” = emit a catch-up delta-trigger event — same bell the webhook fires. No job machine.
  • Profile source-config CRUD + active selection — neutral record shape (shared, not adapter-owned).
  • Status: profile records + source connection state.
  • Common response envelope — same shape for any future source (GDrive/Dropbox).
Decided
  • No third profile service — registry + adapter-hosted surface now; a profile service is a future extension point (not built).
6ra.5.1.1
fetch + gate + land ⇄
Turns FileChangeEvents into staged facts via staging-lib.
▶
Flow per FileChangeEvent
  • created/updated: GET Graph /content (token via 6.6.1) → PDF gate (mimeType application/pdf OR .pdf suffix; skip = no S3 write, no event) → staging-lib land() (5.2.1, layout-versioned keys staging/v1/…) → emit FileStagedEvent.
  • deleted: emit FileDeletedEvent { itemId, relativePath, s3Key: null | removed key } — no fetch.
Owns nothing else

No layout logic (lib does), no index logic (Unit 2 does), no subscription/webhook/delta logic. Idempotent: same event → same s3Key.

Status

Planned — blocked by 6.6.1 (tokens), 6.6.3 (delta events), 5.2.1 (staging-lib).

Business-event registry shared seam · schema-versioned
6ra.5.2.1 Q8 · Q9

The acknowledged cost of the domain-events / consumer-forwarded pattern. Producers (the adapter) emit facts, not commands: “this file was created/updated/deleted — it lived at <relativePath>; I staged it at <s3Key> (or removed it from there)”. Events are centrally registered with schema versions (additive, like the S3 key layout). The registry is not in core — core stays vocabulary-free.

registered
FileStagedEvent · FileDeletedEvent 🔴
CloudEvents 1.0.2 · envelope {type, schemaVersion, emittedAt, payload}.
▶
Registered business events
  • FileStagedEvent: { profileId, source, changeType: created|updated, itemId, name, relativePath, s3Key, mimeType? }
  • FileDeletedEvent: { profileId, source, changeType: deleted, itemId, relativePath, s3Key: string|null }

FileChangeEvent is adapter-internal (delta walk) — not registered. Queue-internal message shapes are domain-owned and never registered.

Decided
  • CloudEvents 1.0.2 structured mode, JSON — envelope format resolved (was Q3, now §4 of the decisions doc).
  • Schema-versioned, additive registration.
Open decisions
  • Q8 — registry transport: DDB event log (outbox-style, consumer-pull) vs SNS/EventBridge (one-hop push to consumer forwarders) vs code-level registry only. The forwarder shape in 5.2.2 follows from it.
  • Q9 — package location: dedicated events package vs inside staging-contracts (rec for now — staging-centric today).
  • Q10 CloudEvents impl: core CE schema vs official SDK.
Resolved during 5.2.1 planning — user reaction needed.

6ra.5.2.2
Index + lifecycle consumer
Consumes registry events → forwards to own queue → updates the index.
▶
Responsibility
  • Upsert file_record → status staged, keyed {profileId, itemId}: FileStaged ⇒ set record; FileDeleted ⇒ remove record.
  • Dedupe under at-least-once: re-Staged same itemId = same record; re-Deleted = no-op.
  • Delete semantics: folders removed only once empty (delta ordering).
  • TTL/cleanup aligned with S3 lifecycle (expire-staged-pdfs).
  • Exposes the “ready files” query surface — delivery (5.2.4) never derives keys.
Status

Blocked by 5.2.1. Forwarder shape follows from registry transport (Q8).

6ra.5.2.3
Dispatch runtime seam
Thin SQS consumer → per-event dispatch; composition root.
▶
Responsibility
  • Parse + validate each event against the seam contracts, apply via 5.2.2.
  • Batch failure semantics (SQSBatchResponse itemIdentifier) — a poison event retries alone; DLQ/redrive.
  • Composition root: the only place that knows runtime config (queue URL, table names, bucket).
  • Provenance/observability: log profileId + itemId + changeType per event.

Thin by design — plumbing, not feature. Successor to the old processor handler. Blocked by 5.2.2.
